# Инструкция для AI-ревьюера: проект Clean Code Todo

## Цель

Проведи ревью итогового решения задания «Clean Code» и найди **смысловые** проблемы, которые не ловит линтер: мёртвый код, дублирование, непонятные имена, комментарии-пересказы, функции, которые не читаются целиком. По каждому замечанию объясни, **почему** это проблема и **как** её проверить.

Ты **аналитик**, а не редактор: не меняй файлы, не предлагай готовых патчей — только анализ и объяснение.

## Границы: что проверять

Проверяй **только** эти файлы:

- `app.js` — основной объект ревью (рефакторинг части 2);
- `index.html` — разметка, семантика, доступность;
- `style.css` — только если правки в нём могли сломать внешний вид.

Проверяй **только** эти категории (из модуля Clean Code и части 2 задания):

1. **Мёртвый код** — неиспользуемые функции, переменные, обработчики, id/классы в HTML, которые нигде не упоминаются.
2. **Дублирование обработчиков** — несколько подписок на одно событие, функции-близнецы, отличающиеся одним параметром.
3. **Дублирование логики** — повторяющиеся блоки, которые можно вынести; **но** проверь, оправдано ли объединение: если похожие блоки решают разные задачи или объединение увеличит число сущностей без выигрыша в читаемости — это не проблема, а осознанное решение (KISS/YAGNI).
4. **Имена** — переменные и функции, которые не читаются без комментария (например, `containsClass`, `editBtn`, `i`, `ul`). Оценивай: понятно ли имя само по себе.
5. **Комментарии** — пересказывают ли код (`//label`, `//toggle .editmode`) или объясняют причину (`//innerText encodes special characters...`). Пересказы — проблема, объяснения причины — нет.
6. **Длинные функции** — читаются ли целиком сверху вниз без переходов. **Не** считай проблемой функцию только за длину: если это линейный сценарий (создать → настроить → собрать → вернуть) без вложенных условий и циклов — дробление может ухудшить читаемость. Проблема — когда функция делает **несколько независимых действий** или требует переходов.

## Границы: чего не трогать

- **Не проверяй настройку инструментов** (`.eslintrc`, `.prettierrc`, `.husky/`, `package.json`, workflow) — это часть 1, её проверяет CI.
- **Не проверяй историю коммитов** — это отдельный блок критериев.
- **Не проверяй поведение приложения** — чек-лист проходит человек на деплое.
- **Не предлагай** переписать на фреймворк, добавить сборщик, сменить архитектуру — это прямо запрещено ТЗ.
- **Не применяй** DRY, KISS, YAGNI «по одному разу» — каждое замечание должно решать **конкретную** проблему, а не демонстрировать знание терминов.
- **Не правь файлы** — только анализируй.

## Критерий готовности

Ревью закончено, когда:

- проверены все шесть категорий выше по `app.js`, `index.html` и (при необходимости) `style.css`;
- по каждой найденной проблеме есть запись в отчёте по формату ниже;
- по каждой категории явно сказано: «проблем не найдено» **или** перечислены замечания;

## Формат вывода

Создай файл `review-report.md` в корне проекта. Язык — **русский**. Структура:

```markdown
# Отчёт AI-ревьюера

## Сводка

- Проверено файлов: …
- Найдено проблем: … (по категориям: мёртвый код — N, дублирование — N, имена — N, комментарии — N, длинные функции — N)
- Категории без замечаний: …

## Замечания

### 1. [Категория] Краткое название

- **Место:** `app.js`, строки 12–18 (или `index.html`, строка 42)
- **Проблема:** что не так и почему это проблема с точки зрения Clean Code
- **Условие проявления:** при каком сценарии/правке это станет больно (например: «при добавлении третьего списка придётся править обе функции-близнеца»)
- **Как проверить исправление:** конкретный шаг — поиск по коду, прогон чек-листа, взгляд на diff

### 2. …

## Категории без замечаний

- Длинные функции: `createTaskItem` и `editTask` читаются целиком, дробление не требуется — обоснование в описании PR.
- …
```
